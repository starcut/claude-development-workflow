# Flutter / Dart Code Quality Rules

## 1. 強制アンラップを原則として使用しない

Dartの強制アンラップ演算子 `!` を原則として使用しない。

Nullableな値は、以下のような安全な方法で処理する。

- nullチェック
- if
- switch
- 早期return
- null-aware operator
- デフォルト値
- 型や設計の見直し

「必ず値が存在する」という開発者の判断だけを根拠として、
`!` を使用しない。

ただし、フレームワークやAPIの仕様上、値の存在がコード上明確に保証され、
`!` の使用が合理的である場合は、その根拠を確認した上で使用を判断する。


## 2. dynamicの安易な使用を避ける

`dynamic` は必要性が明確な場合にのみ使用する。

可能な限り具体的な型を使用し、
コンパイル時に型安全性を確保できる設計を優先する。


## 3. FlutterのWidget責務を明確にする

Widgetに過剰な処理責務を持たせない。

特に以下のような処理は、Widgetの責務として適切か確認する。

- ビジネスロジック
- データ取得
- 永続化処理
- 複雑な状態管理
- 外部サービスとの直接的な通信

プロジェクトで定めたアーキテクチャおよび状態管理方式に従い、
適切な層へ責務を分離する。


## 4. BuildContextの扱いに注意する

非同期処理の後に `BuildContext` を使用する場合は、
Widgetのライフサイクルやcontextの有効性を考慮する。

非同期処理前に取得したcontextを、
Widgetが破棄された可能性のある状態で無条件に使用しない。

必要に応じて、プロジェクトで採用しているFlutter/Dartの
ライフサイクル上の安全な方法を使用する。


## 5. Flutter固有のライフサイクルを考慮する

`initState`、`dispose`、`build` 等のライフサイクルを理解した上で実装する。

特に以下について、不適切な実装を避ける。

- `build` 内での副作用
- `dispose` 後の処理
- ListenerやSubscriptionの解除漏れ
- Controller等の解放漏れ
- Widgetの再構築による意図しない処理の繰り返し

Widgetのライフサイクルに依存するリソースは、
生成・利用・破棄の責務を明確にする。


## 6. 不要な再ビルドを避ける

Widgetの再ビルドが発生することを前提とし、
`build` 内に不要な重い処理や副作用を配置しない。

状態管理を使用する場合は、
必要なWidgetだけが状態変更の影響を受ける構造を検討する。

ただし、再ビルドを減らすこと自体を目的として、
不要に複雑な最適化を行わない。


## 7. constを適切に使用する

Flutterでコンパイル時に確定できるWidgetや値については、
`const` の利用を検討する。

ただし、すべての箇所で機械的に `const` を追加することを目的としない。

コードの可読性と既存プロジェクトの方針を優先する。
