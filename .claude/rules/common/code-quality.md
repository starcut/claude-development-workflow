# Code Quality Rules

## 1. マジックナンバーの禁止

コード中に意味が明確でない数値リテラルを直接記述しない。

意味を持つ値は、用途が分かる名前の定数または変数として定義する。

### Bad

if (items.length > 10) {
  ...
}

### Good

const maxItemCount = 10;

if (items.length > maxItemCount) {
  ...
}

ただし、0、1、-1など、文脈上意味が明確な値まで機械的に定数化しない。

値そのものに意味がある場合、または変更される可能性がある場合は定数化する。


## 2. 意味を持つ文字列のハードコーディング禁止

意味を持つ文字列をコード中に直接記述しない。

繰り返し使用する文字列、状態値、識別子、設定値、エラーメッセージ等は、
用途が明確になる形で管理する。

### Bad

if (status == 'visited') {
  ...
}

### Good

const visitedStatus = 'visited';

if (status == visitedStatus) {
  ...
}

ただし、単発のUI表示文言を機械的にすべて定数化しない。

多言語化の対象となるUI文言は、プロジェクトで定めた
ローカライズの仕組みに従って管理する。


## 3. 1ファイル300行以内

原則として、1ファイルの実装コードは300行以内とする。

300行を超える場合は、単純に行数を削減するのではなく、
ファイルの責務が複数に分かれていないかを確認する。

必要に応じて責務単位での分割を検討する。

ただし、300行を超えたことだけを理由として、
意味のない細分化やファイル分割を行わない。

行数よりも責務の明確さを優先する。


## 4. デバッグ用コードを残さない

デバッグ目的の出力や一時的なデバッグコードを本番コードに残さない。

ログ出力が必要な場合は、プロジェクトで定めたLogging方式を使用する。

一時的なデバッグコードを追加した場合は、
作業完了時に不要なコードが残っていないことを確認する。


## 5. 不要なコードを残さない

未使用のimport、変数、メソッド、クラス、コメントアウトされたコード等を
不要な状態で残さない。

既存コードを変更・削除した際には、
変更によって不要になったコードも確認する。

ただし、将来使う予定という理由だけでコードを残さない。


## 6. 不要なコメントを追加しない

コードから処理内容が明らかな場合、
その内容を説明するだけのコメントを追加しない。

コメントは、主に以下のような場合に使用する。

- なぜその実装にしているのか
- 一見すると不自然だが必要な処理
- 外部仕様や制約による特殊な実装
- 将来変更する際に注意すべき事項

コメントによってコードの理解を補助することを目的とし、
コメントでコードの複雑さを隠さない。


## 7. 不要な重複実装を避ける

同一または実質的に同一の処理を複数箇所に実装しない。

複数箇所で同じ処理が必要な場合は、共通化を検討する。

ただし、共通化によってコードの責務や依存関係が複雑になる場合は、
無理な共通化を行わない。

コードの重複削減よりも、責務の明確さと可読性を優先する。


## 8. 例外を理由なく握り潰さない

catchした例外を理由なく無視しない。

例外を処理する場合は、状況に応じて以下を検討する。

- 適切なエラー状態への変換
- ログ出力
- 上位層への伝播
- 再throw

例外を処理する必要がないことが設計上明確な場合を除き、
空のcatchや、例外を無視するだけの処理を作らない。
